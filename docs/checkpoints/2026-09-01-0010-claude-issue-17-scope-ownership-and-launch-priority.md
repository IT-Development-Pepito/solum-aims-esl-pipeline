- **The business decision was put to the user before implementation, not assumed.** The documentation deliberately permits either outcome for a contended attempt: WORKFLOW said "reject or explicitly queue", and FR-009's acceptance says "one explicit rejected/queued outcome". The user chose reject with no execution created. Two facts framed that choice and are recorded in PROGRESS: the approved state graph allows only `QUEUED -> RUNNING`, so a queued contender could never be cancelled or expired, and nothing yet starts queued work, so the rows would accumulate unseen. Rejecting also matches the VERIFIED legacy behaviour, where an already running SQL Agent job does not stack another invocation.
- **The policy is symmetric on purpose.** FR-017 asks for a defined priority between scheduled and manual operations, and the only approved answer today is that neither preempts the other. `decide_ownership` records both the requested and the held trigger type but neither influences the outcome, and a parameterized test iterates every trigger-type pair precisely so that any future preemption would fail a test rather than pass silently. Any preference beyond this is UNKNOWN / NEEDS-DISCOVERY and would be the unapproved priority override the issue's non-goals exclude.
- **Acceptance criteria:** Exactly one owner and one explicit refusal is verified against real rows, including that only one `scope_lease` exists for a contended scope and that the loser creates no `workflow_execution`. Manual-versus-scheduled is verified in both directions. Decision, owner, and outcome are audit-visible through `scope.granted` and `scope.rejected` entries carrying the policy version, scope key, both trigger types, and the owning execution id; a rejection has no `execution_id` because no execution exists.
- **Ordering correctness:** the ownership check produces the explicit, auditable decision, but the atomic claim from #1 remains the durable guarantee. The execution insert runs inside a savepoint and is rolled back if the claim loses a race after the check passed, so no execution can ever exist without owning the scope it was created for. That `ScopeContention` branch is defensive and is **not** covered by an automated test: reproducing it needs two committed concurrent transactions, which the rollback-based integration fixtures exclude by design. This is recorded in PROGRESS rather than left implied.
