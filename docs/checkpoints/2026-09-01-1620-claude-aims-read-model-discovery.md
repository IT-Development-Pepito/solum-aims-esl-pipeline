- **The read model, and a correction to #22.** Page assignment lives in `AIMS_PORTAL_DB.end_device_templates (label_code, name, page, station_code)`, keyed `(label_code, page)`. The three fields the #22 `AimsLabel` port carries turned out to be the right ones, which is a useful confirmation of a port written before any AIMS access existed. But its `station_code` is **not** a store code: all 10,834 rows hold the literal `DEFAULT_STATION_CODE`. The real store code is on `end_device` and `end_device_articles`, so `fetch_labels(store_code)` must join rather than filter the template table. The primary key also permits several pages per label, so the port returns multiple rows per `label_code` even though its name reads as one row per label; that is noted on #22 rather than changed here.
- **Portal depends on Core through postgres_fdw.** `AIMS_PORTAL_DB` carries the extension, the server `fdw_aims_core_db`, an `aims` user mapping, and foreign tables `enddevice`, `slabel`, and `station`, with a materialized view `enddevice_info` built on them. The adapter should read both databases directly instead, so we do not depend on vendor-internal connection configuration that can change without notice. One naming trap is recorded because it will otherwise cause a subtle bug: Portal has both `end_device`, its own table, and `enddevice`, a foreign table from Core.
- **Store 075 is effectively not fitted.** AIMS holds 15,010 `article` rows for it but only 2 `end_device` rows, against 10,832 for `084`. This reconciles with the existing evidence that the Hop pipeline constrains its SQL to `084`: store `075` is computed by SQL Server and never reaches AIMS. The source owner confirmed this is intentional for now. It is recorded because a parity comparison would otherwise report every 075 label as missing and read as a defect.
- **A real production data defect was found.** `article_id = 101066052139` has `station_code = '"075'`, four characters with a leading double quote, which silently escapes an exact-match filter on `075`. It is recorded rather than fixed, since AIMS is vendor-owned and writing to it is prohibited. It makes a useful fixture for the structural validation built in #12.
- **One finding deliberately left UNKNOWN.** Every `end_device_templates` row has `page = 0`, while the Hop pipeline `esl-sku-promo-multi-page.hpl` is documented as enabling Page 3. Those cannot both describe the same field, so the likely reading is that `end_device_templates.page` is a template slot while the displayed page sits in `AIMS_CORE_DB.enddevice.pages`, a `varchar(100)`. That table could not be read because the `AIMS_CORE_DB` grant for the local reader role is still outstanding, so the question is recorded as UNKNOWN rather than answered by inference.
