- **What the procedure does, and what moved where.** `RefreshESL_New` joins `[192.168.85.18].[PEPITO_HO].dbo.ITEM_UOM_MAPPING_MST` on item code with three predicates: `IUM_UOM_MAP_STATUS = 'O'`, `IUM_MAIN_ITM_BARCODE = 1`, `IUM_SALES_UOM_FLAG = 1`. Those choose the selling UOM and barcode, which is the #36 rule set, so the adapter does not apply them: it returns every mapping row for the requested item set, raw, and a row the domain rejects is recorded with its reason. The only data predicate is the item set, chunked at 500 codes inside one transaction, because the table is central and has no store column; an empty set is refused at the port (`UomMappingReadRequest`), since an unbounded read of a central table is never what a caller means.
- **A real finding, and the decision it forced (AD-020).** The first live read failed with SQL Server error 3952: snapshot isolation is not allowed in `PEPITO_HO`. A read-only catalog query then showed `snapshot_isolation_state = OFF` on all three source databases (`PEPITO_HO`, `DBWH_8555`, `ESL`), so the `SNAPSHOT`-only engine merged with #91 could read nothing either. Three options were put to the owner: `READ COMMITTED` recorded in provenance (recommended), a DBA change to enable snapshot isolation on production, or the legacy `NOLOCK`. The owner chose `READ COMMITTED`. Consequences: a new setting `ESL_SOURCE_SQL_ISOLATION_LEVEL` (`READ COMMITTED` default, `SNAPSHOT` allowed), a new `isolation_level` field on `WarehouseProvenance` so every read states what it ran under, and the #91 engine now taking its level from configuration. `SYSTEM_ARCHITECTURE` section 5 no longer says the adapter "fails safely rather than falling back": it reads under the configured level and records it.
