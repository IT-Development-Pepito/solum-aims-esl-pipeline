- **Design, as approved:** raw source rows are not retained (AD-005), so a snapshot replay is *reproducibility evidence*, not recomputation. New `TriggerType.SNAPSHOT_REPLAY`; `SnapshotReplayRequest` (identity and reason, no window); pure `decide_snapshot_replay` refusing `SNAPSHOT_EVIDENCE_MISSING` (no finalized `SOURCE_EXPECTED` capture) or `RECONCILIATION_UNRESOLVED` (latest report not final), the refusal audited as `workflow.snapshot_replay.refused`; `LaunchRepository.launch_snapshot_replay` creating the linked run under the original's window, configuration version, rule version, and mode, with the source capture id and hash in the launch audit evidence. `application/replay.py`: one step `replay-snapshot` copying the retained records verbatim (`SnapshotRepository.copy_record`) into a new capture, finalizing it, recording `SNAPSHOT_REPLAYED` with both aggregate hashes and `hash_reproduced`, hash-decided differences against the store's current expected state, and a balanced report with drifted records `ineligible` and `intended` zero; idempotent through the same finalized-capture guard as `persist_run`. The runner branches on the trigger to that single step and ends `SUCCEEDED_WITH_EXCEPTIONS` when the hash did not reproduce. `AuthorizedOperations.replay_snapshot` under `Operation.REPLAY`; `esl-admin runs replay-snapshot <id> --reason`; `POST /runs/{id}/replay-snapshot` with a reason only. Differences compare to the store's latest finalized capture excluding the replay itself, as persist does, so a replay also answers what changed since that run.
